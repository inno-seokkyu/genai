## 1. 문제 정의

회의가 끝나면 누군가가 메모를 정리해 공유해야 하지만 실제로는 다음 문제가 반복됩니다.

- **결정과 논의가 섞입니다.** "얘기 나왔음"이 "하기로 함"으로 바뀌어 공유되고, 나중에 "그거 확정 아니었는데요?"가 발생합니다.
- **담당자·기한이 빠진 할 일이 생깁니다.** "누가 물어보기로"처럼 담당이 없는 항목은 아무도 하지 않습니다.
- **정리에 시간이 걸립니다.** 1시간 회의를 정리하는 데 20~30분이 듭니다.

그냥 LLM에 "요약해줘"라고 하면 문장은 매끄럽지만, 위의 첫 두 문제를 오히려 숨깁니다. 빠진 담당자를 그럴듯하게 채우거나 보류 사항을 결정으로 요약하는 식입니다. 이 봇의 목표는 **빠르게 정리하되, 원문에 없는 것은 만들지 않고 "확인 필요"로 드러내는 것**입니다.

## 2. 타겟 사용자

| 항목 | 내용 |
|---|---|
| 주 사용자 | 사내 프로젝트의 PM, 팀 리드, 회의록 담당자 |
| 사용 상황 | 주간 회의, 킥오프, 이슈 회의 직후 메모나 녹취 요약을 정리해 팀·상위 보고자에게 공유할 때 |
| 기대 효과 | 정리 시간 단축, 결정/보류 구분 명확화, 담당 없는 할 일을 바로 발견 |

## 3. 입력·출력 규격

**입력 데이터 형태**: 비정형 텍스트 회의 메모(발언자 역할 + 발언 요지 불릿) 또는 녹취 요약문. 추가로 톤·대상·금지 사항 같은 조건.

**출력 규격**: Markdown. 아래 섹션을 항상 이 순서로 출력하고, 내용이 없으면 "없음"으로 표시합니다.

```
## 회의 요약 | {회의명} ({YYYY-MM-DD})
**참석(역할)**: …
### 1. 결정사항
### 2. Action Items   ← 표: # | 할 일 | 담당(역할) | 기한 | 비고
### 3. 보류·추가 논의
### 4. 리스크
### 5. 후속 일정
### 6. 확인 필요
### 핵심 근거        ← 원문 인용 3개, 각 1줄
```

## 4. 업무 과업 입력 템플릿 (재사용용)

아래를 복사해 대괄호 안만 채워 쓰면 됩니다.

```
[업무 과업] 회의록 요약
[회의명/날짜] (예: 러닝허브 리뉴얼 주간 회의 / 2026-10-12)
[원문] (회의 메모 또는 녹취 요약을 그대로 붙여넣기)
[공유 대상] (예: 팀 내부 / 본부장 보고 / 슬랙 공지)
[원하는 결과] 결정사항 / Action Items / 보류 / 리스크 / 후속 일정
[톤] (예: 간결, 사내 공유용 / 단호하게)
[금지] 추측성 표현, 실명 사용(역할명만), 원문에 없는 담당자·기한 생성
[분량] (예: 제한 없음 / 5줄 이내)
[확인 질문 규칙] 정보가 부족하면 최대 3개까지 질문. 요약이 가능하면 먼저 요약하고 빈 칸은 "확인 필요"로 표시
```

## 5. 페르소나

| 항목 | 정의 |
|---|---|
| 이름 | 미닛 (Minit) |
| 역할(직무) | 10년차 PMO 출신 회의록 정리 전문가 |
| 전문 분야 | 회의록 구조화, 실행 항목(Action Item) 관리, 일정·예산 정합성 확인 |
| 말투 | 합니다체, 불릿 중심, 간결함. 이모지와 과한 인사말 없음 |
| 금지 사항 | 원문에 없는 담당자·기한·금액 생성, 보류 사항을 결정으로 기재, 추측성 표현, 실명 등 개인정보 사용, 사내 규정 추정 |
| 우선순위 | **정확성 > 형식 준수 > 간결함 > 친절함** |

**왜 이 페르소나인가**: PMO는 "누가, 언제까지"가 없는 할 일을 가장 싫어하는 직무입니다. 이 성향을 페르소나로 부여하면 담당·기한 누락을 드러내는 행동이 자연스럽게 강화됩니다. 우선순위를 명시한 이유는, 사용자가 "보기 좋게 채워줘"라고 요청할 때(친절함) 정확성이 이기도록 하기 위해서입니다.

## 8. 환각 검증 설계

**정의**: 사실·수치·정책·계산처럼 정답이나 검증 가능한 근거가 있어야 하는 질문에서, 근거 없이 틀린 정보를 확신하는 답변.

**판정 규칙**
- **Pass**: (A) 정답 + 간단한 근거 제시, 또는 (B) 모르면 "모른다/확인 필요"를 밝히고 확인 절차 제안
- **Fail**: 틀린 사실을 단정하거나, 전제가 불명확한데 확인 없이 사실을 만들어 답함

## 9. 단계적 추론 유도: v1 → v2 개선 이력

### v1 (Zero-shot, 간단 지시)
```
아래 회의 내용을 요약해줘.
(회의 메모)
```
- 페르소나, 출력 형식, 사실 처리 규칙, 예시 없음

### v2 (페르소나 + 단계적 추론 + Few-shot)
| 변경 | 이유 (v1에서 예상·관찰된 문제) |
|---|---|
| 페르소나·우선순위 추가 | 친절함을 위해 빈칸을 그럴듯하게 채우는 경향을 억제 |
| 5단계 내부 작업 절차 추가 (조건 확인 → 결정/논의/보류 구분 → 담당·기한 확인 → 확인 질문 → 원문 대조) | 보류 사항이 결정으로 섞이는 문제, 담당 미정 항목 누락 방지 |
| "과정은 출력하지 말고 핵심 근거 3개만" 규칙 | 단계적 추론이 장문으로 그대로 노출되는 것을 방지 |
| 고정 출력 템플릿 + "확인 필요" 섹션 | 모델·실행마다 형식이 달라지는 문제, 누락 정보가 묻히는 문제 |
| 사실·수치·정책 규칙 (계산식, 법령 근거, 사내 규정 추정 금지, 거짓 전제 정정) | 환각 검증 Q3~Q6 유형 대응 |
| Few-shot 3개 (표준 / 수치·보류 / 모호한 입력) | 규칙만으로는 "확인 필요" 표기 방식과 되묻는 수준이 일정하지 않음 |
| 대화 규칙 ("반영한 변경", "(갱신)") | 10턴 대화에서 조건 변경 시 기존 조건이 사라지는 문제 대응 |

### v1 vs v2 실측 비교 (동일 입력, 3개 모델, 2026-10-14)

원본: `logs/raw/A_v1_*.md`, `logs/raw/B_v2_*.md` / 모델별 상세 비교: `docs/01_model_comparison.md` 5.3

| 점검 항목 | v1 결과 (3개 모델) | v2 결과 (3개 모델) |
|---|---|---|
| 12월 연기를 보류로 분류했는가 | 3/3 | 3/3 |
| 결제 모듈 담당을 "미정/확인 필요"로 남겼는가 | 3/3 | 3/3 |
| 마케팅 700만원을 미확정으로 분류했는가 | 3/3 | 2/3 (ChatGPT가 결정사항 섹션에 넣고 "미승인"이라고 표기) |
| **원문에 없는 담당·기한을 만들어 넣은 건수** | **7건** (ChatGPT 3, Claude 2, Gemini 2) | **1건** (Gemini: PM 품의 기한 10/16) |
| 출력 형식 일관성 | 모델마다 제각각 (이모지 섹션, 카드형 예산, 종합 의견 등) | 3/3이 같은 6섹션 템플릿 + 핵심 근거 3개 |
| 확인 질문 | 0/3 | 1/3 (Claude만 마지막에 질문 3개) |
| 추론 과정 노출 | 해당 없음 | 요약에서는 0/3. 단, Gemini가 Run C에서 코드 실행 과정을 노출 |

**해석**
- v1도 "결론 안 남", "담당 미정"처럼 **원문에 명시된 것**은 잘 지켰습니다. 문제는 **원문이 침묵하는 곳**이었습니다. 표의 담당·기한 칸을 비워 두지 않으려고 발언자(PM)나 관련 직무(백엔드, 디자인)를 담당으로 지정했습니다. 회의록에서는 이런 "그럴듯한 빈칸 채우기"가 가장 위험한 오류입니다.
- v2의 "원문에 없는 담당·기한은 만들지 않고 확인 필요로 표시" 규칙과, 그것을 보여 주는 Few-shot 1(연사 섭외 기한 "확인 필요")이 이 오류를 7건에서 1건으로 줄였습니다.
- 반면 "마지막에 확인 질문" 절차는 1개 모델만 따랐습니다. 규칙만 있고 Few-shot 1·2에는 질문 예시가 없기 때문으로 보입니다. Few-shot 3(모호한 입력)에만 질문이 있어서, 모델들이 "원문이 있으면 질문하지 않는다"고 배웠을 수 있습니다. → v2.1 후보로 기록합니다.

## 10. 한계와 운영 시 주의

- 웹 UI에서는 temperature 같은 생성 설정을 바꿀 수 없어 기본값으로 실행했습니다. 같은 입력이라도 실행마다 결과가 달라질 수 있습니다.
- 시스템 프롬프트를 첫 사용자 메시지로 전달했기 때문에, 대화가 아주 길어지면 지시의 영향력이 약해질 수 있습니다.
- 법령 답변은 참고용이며, 실제 적용 전에는 국가법령정보센터나 사내 노무 담당에게 확인해야 합니다.
